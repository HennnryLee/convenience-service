## 1. 数据库版本化（Flask-Migrate / Alembic）

项目早期用 `db.create_all()` 建表，适合首次演示，但不适合生产环境的平滑升级。
现在引入 Flask-Migrate，迁移脚本位于 `migrations/`：

| 版本 | 内容 |
| --- | --- |
| `7c0a74a1027b` | 初始结构：users / services / appointments / announcements / feedbacks |
| `798d0427d9c2` | 新增 `audit_logs` 审计表 |

### 1.1 全新数据库

```bash
flask --app "app:create_app" db upgrade
```

### 1.2 已有数据库（重要，先备份）

已有 `instance/app.db` 已经包含初始 5 张表，但还没有 `alembic_version`。
**不要直接 `flask db upgrade`**（初始迁移会重复建表而失败）。两种安全路径：

**路径 A：标记到初始版本，再执行审计表迁移（推荐）**

```bash
cp instance/app.db instance/app.db.bak
flask --app "app:create_app" db stamp 7c0a74a1027b
flask --app "app:create_app" db upgrade        # 只创建 audit_logs
```

**路径 B：先用 create_all 补表，再标记为最新**

```bash
cp instance/app.db instance/app.db.bak
python run.py --init-db                       # 幂等；只新增缺失的 audit_logs
flask --app "app:create_app" db stamp head
```

> `--init-db` 和迁移脚本都**不会删除已有数据**。执行前仍建议备份；
> 迁移前请确认 `DATABASE_URL` 指向目标库，不要误连开发库。

### 1.3 后续结构变更流程

```bash
# 1) 修改 models 后生成迁移（先 review 生成的脚本！）
flask --app "app:create_app" db migrate -m "add xxx field"

# 2) 在测试库上演练
flask --app "app:create_app" db upgrade

# 3) 退化验证（可选，确认 downgrade 可用）
flask --app "app:create_app" db downgrade

# 4) 生产执行（先备份）
flask --app "app:create_app" db upgrade
```

`migrations/env.py` 由 Flask-Migrate 生成，已与 `db.metadata` 绑定；
迁移脚本必须提交到 Git，和代码同版本交付。

## 2. 审计日志

管理员在后台的写操作会写入 `audit_logs`：

| 动作码 | 场景 | 记录内容 |
| --- | --- | --- |
| `service.create` | 新增服务 | 名称、分类、目标 id |
| `service.update` | 编辑服务 | 名称、分类、目标 id |
| `service.toggle` | 服务上下架 | 新状态 |
| `user.toggle` | 用户启用/禁用 | 用户名、是否启用 |
| `appointment.status` | 预约状态推进 | 原状态、目标状态 |
| `announcement.create` | 发布公告 | 标题、目标 id |

每条记录包含：操作者 id/用户名、动作、目标类型/id、详情、IP、`X-Request-ID`、时间。
后台入口：`/admin/audit-logs`（只读，可按动作筛选）。

设计要点：

- **只追加**：不提供修改/删除接口，避免业务代码覆盖审计记录；
- **冗余 actor_username**：用户改名/删除后仍能回答“当时是谁做的”；
- **request_id 关联**：可与 `instance/logs/app.log` 的访问日志按同一 ID 对齐；
- **失败降级**：审计写入失败只记 ERROR 日志并回滚审计事务，
  不阻断管理员的主操作（`app/services/audit_service.py`）。

清理策略建议：审计表按年归档，不要直接在业务库 `DELETE`；
可导出 CSV 后迁移到独立审计库。

## 3. 生产部署拓扑

```
浏览器 --HTTPS--> Nginx (TLS/静态资源) --HTTP--> Gunicorn (wsgi:app) --SQL--> MySQL 8.0
```

### 3.1 环境变量

```bash
export FLASK_CONFIG=production
export SECRET_KEY="$(python -c 'import secrets;print(secrets.token_hex(32))')"
export DATABASE_URL="mysql+pymysql://convenience:密码@127.0.0.1:3306/convenience?charset=utf8mb4"
export LOG_LEVEL=INFO
export WEB_WORKERS=4
```

生产配置会强制要求非默认 `SECRET_KEY`，并启用 `SESSION_COOKIE_SECURE` /
`REMEMBER_COOKIE_SECURE`；HTTPS 请求自动追加 HSTS。

### 3.2 安装与启动

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-prod.txt

flask --app "app:create_app" db upgrade
flask --app "app:create_app" check-db

gunicorn -c deploy/gunicorn.conf.py wsgi:app
# 或 systemd：deploy/generated/convenience.service（由模板渲染）
```

Windows 开发机可用：

```bash
pip install waitress
waitress-serve --call "app:create_app"
```

### 3.3 Nginx

参考 `deploy/nginx.conf.template`，用 `deploy/render_configs.py` 按环境变量渲染：

- 80 端口 301 到 HTTPS；
- 443 终止 TLS，`X-Forwarded-Proto https`；
- `/static/` 由 Nginx 直出并缓存 7 天；
- `client_max_body_size 2m`（与应用 1 MB 上限匹配）；
- 透传 `X-Request-ID`，与应用访问日志对齐。

### 3.4 健康检查与监控

- `GET /healthz`：数据库可用返回 `200 {"status":"ok","database":"ok"}`，
  不可用返回 `503 {"status":"degraded","database":"error"}`；
- `flask --app "app:create_app" check-db`：人工检查连接、表结构、各表行数；
- `instance/logs/app.log`：滚动日志，5xx 带 request_id 与堆栈（仅日志，不返回给用户）。

## 4. 发布与回滚清单

| 步骤 | 命令/检查 |
| --- | --- |
| 1. 备份 | `mysqldump` 或复制 `instance/app.db` |
| 2. 拉代码 | `git pull --ff-only` |
| 3. 安装依赖 | `pip install -r requirements-prod.txt` |
| 4. 迁移 | `flask --app "app:create_app" db upgrade` |
| 5. 自检 | `flask --app "app:create_app" check-db`、`curl https://站点/healthz` |
| 6. 重启 | `systemctl reload convenience` 或 `kill -HUP <gunicorn master>` |
| 7. 回归 | `pytest`、`ruff check`、人工冒烟（登录/查询/预约/后台） |
| 8. 回滚 | `git checkout <上一个 tag>`；数据库按备份恢复或 `db downgrade -1` |

> 生产发布前至少保留一次“真实配置 + 人工 β 测试”的冒烟路径（教材 9.2.5 的教训：
> 自动化全绿不等于用户能用）。

## 5. 审计归档与夜间任务

### 5.1 审计归档

审计表只追加，长期运行会持续增长。归档脚本先导出 CSV，默认**不删除**；
确认文件无误后再加 `--delete`：

```bash
# 1) 导出 2026-01-01 之前的记录
python scripts/archive_audit_logs.py --before 2026-01-01

# 2) 检查 instance/audit_archive_20260101.csv

# 3) 确认后删除已归档记录
python scripts/archive_audit_logs.py --before 2026-01-01 --delete
```

生产库操作前务必先备份；审计归档文件建议转存到独立存储/审计库。
实现见 `app/services/audit_archive.py`（先导出后删除，导出失败不删除）。

### 5.2 夜间任务

`.github/workflows/nightly.yml` 每天 02:00（Asia/Shanghai）执行：

1. 迁移演练 + 全量 pytest + 覆盖率 + 静态检查；
2. 临时演示库启动真实服务，`/healthz` 探活；
3. Locust 20 用户 30 秒性能冒烟；
4. Chrome/Edge/Firefox 兼容性检查（无浏览器的环境自动跳过）；
5. 上传 `reports/` 产物。

也可手动触发 `workflow_dispatch`。注意夜间任务使用临时 SQLite 库，不接触生产库。
