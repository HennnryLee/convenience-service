# 契约式编程与断言实践

> 依据：《基于案例的软件构造教程》4.3.1 防御性编程、4.3.2 使用断言、4.9.3 契约式编程
> 实现：`app/utils/contracts.py`、`app/services/appointment_rules.py`
> 测试：`tests/unit/test_contracts.py`（15 条）

## 1. 教材要点回顾

教材把"健壮的程序"拆成三个递进的层次，本系统逐一落地：

| 层次 | 教材论述 | 本系统落地 |
| --- | --- | --- |
| 防御性编程（4.3.1） | 检查每个输入参数，特别检查来自用户交互、文件、数据库、网络的数据 | `app/utils/validators.py`、各 FlaskForm 的 `DataRequired/Length/Regexp`、`validate_basic_fields()` |
| 断言（4.3.2） | 断言是让程序在运行过程中自我检查的代码，分**前置断言、后置断言、不变断言** | `app/utils/contracts.py` 的 `require / ensure / invariant` |
| 契约式编程（4.9.3） | 用"三个问题"描述模块：期望什么（前置条件）、保证什么（后置条件）、保持什么（不变式） | 业务规则函数头部的契约声明 + `docs/06` 的契约表 |

教材特别强调两条使用原则，本系统严格遵循：

1. **"对预计出现的条件使用错误处理，对不应当出现的条件使用断言"**
   —— 用户填错表单属于"预计出现"，返回错误列表；调用方传错类型属于"不应当出现"，直接违约。
2. **"程序部署完之后就关闭断言"**
   —— `CONTRACT_CHECK=0` 时全部契约短路，不执行条件求值，零运行期开销。

## 2. 断言三分类在本系统中的实例

| 类型 | 含义 | 代码位置 | 具体断言 |
| --- | --- | --- | --- |
| 前置断言 | 代码执行前必须具备的特性 | `validate_new_appointment` | `context` 必须是 `AppointmentContext`；`appointment_date` 必须是 `date` 或 `None`；`max_days_ahead` 必须是正整数 |
| 后置断言 | 代码执行后必须具备的特性 | `validate_new_appointment` | 返回值必须是列表，且每条都是非空字符串 |
| 后置断言 | 同上 | `remaining_capacity` | `0 <= 返回值 <= capacity`（超卖时不返回负数） |
| 不变断言 | 执行前后不能变化的特性 | `validate_new_appointment` | `TIME_SLOTS` 时段表在校验过程中不得被修改 |

## 3. 契约三问的落地（以预约校验为例）

| 契约要素 | 教材定义 | `validate_new_appointment` 的契约 |
| --- | --- | --- |
| 前置条件（客户的义务） | 调用方必须保证的进入条件 | 传入装配好的上下文、合法日期类型、正整数窗口期；不满足即**调用方违约**，抛 `ContractViolation` |
| 后置条件（供应商的义务） | 退出时必须给出的属性 | 返回错误列表；空列表表示通过；错误信息非空 |
| 不变式 | 进入时假定、退出时保持 | 不修改入参；不修改全局时段表 |

调用关系就是教材所说的"客户—供应商"关系：`appointment_service.create_appointment` 是客户，
`appointment_rules` 是供应商。客户若提供了 `{"service_online": True}` 这样的字典，供应商不再
"猜"着处理，而是立即失败——把 bug 暴露在离缺陷最近的地方，而不是让它变成一条错误的预约记录。

## 4. 违约行为验证（测试）

`tests/unit/test_contracts.py` 用 15 条用例把上述契约全部钉死：

| 用例 | 验证点 |
| --- | --- |
| `test_require_raises_on_violation` | 违约抛 `ContractViolation`，且它是 `AssertionError` 子类（与内置断言语义一致） |
| `test_contract_can_be_disabled` | 设置 `CONTRACT_CHECK=0` 后契约短路（模拟发布版） |
| `test_remaining_capacity_contract_rejects_negative` | 负数容量/占用触发前置违约 |
| `test_remaining_capacity_contract_rejects_non_integer` | 浮点容量触发前置违约（类型错误不静默通过） |
| `test_remaining_capacity_postcondition_holds_for_all_valid_inputs` | 穷举 `capacity∈[0,5] × used∈[0,8]` 共 54 组，验证后置条件恒成立 |
| `test_validate_new_appointment_rejects_wrong_context` | 传字典而非上下文 → 立即失败 |
| `test_validate_new_appointment_postcondition_returns_non_empty_strings` | 后置条件成立，错误项均为非空字符串 |
| `test_state_query_contract_requires_string` | 状态查询传 `None` → 违约 |

## 5. 与"防御性编程"的分工

| 场景 | 处理方式 | 理由 |
| --- | --- | --- |
| 用户提交空日期、手机号少一位、密码太短 | 返回友好的错误提示列表 | 属于**预计出现**的输入错误，不应让程序崩溃 |
| 关键词超长（>50 字） | 返回空结果 + 页面提示 | 教材 4.3.1"用最接近的有效数据替换无效数据"的变体 |
| 未知分类码 / 未知状态码 | 回退为"其它"/"未知状态" | 外部数据不可信，采用"中性无害"的默认值 |
| 业务函数收到错误类型的上下文 | 抛 `ContractViolation` | 属于**不应当出现**的编程错误，必须 fail-fast |

## 6. 收益与代价

**收益**

- 契约写在函数入口，读代码即可知道"能传什么、会返回什么"，无需读实现；
- 缺陷定位成本降低：违约栈直接指向调用方，而不是几层之后的数据错乱；
- 与单元测试互补：测试验证"符合契约时的行为"，契约保证"不符合契约时不会静默出错"。

**代价**

- 契约条件本身需要维护，可能随实现漂移；
- 运行期有少量判断开销（可用 `CONTRACT_CHECK=0` 关闭）；
- 契约不能替代测试：它只检查"声明过的性质"，无法证明结果在所有输入下正确。
