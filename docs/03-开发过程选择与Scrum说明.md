# 便民服务平台 · 开发过程选择说明

> 对应《软件构造》实验一第 2、3 条要求

## 1. 为什么选择增量迭代而不是瀑布模型

| 对比维度 | 瀑布模型 | 增量迭代模型 | 本项目情况 |
| --- | --- | --- | --- |
| 需求稳定性 | 要求需求一开始完全确定 | 允许需求逐步细化 | 便民服务需求只给出模块清单（用户管理、服务查询、在线预约…），细节（如预约时段容量、状态流转）需在开发中明确 |
| 交付节奏 | 末期一次性交付 | 每个迭代交付可用增量 | 课程实验本身就按 5 个实验分批提交，天然增量 |
| 风险暴露 | 风险在集成阶段集中爆发 | 每个迭代都能验证，早期暴露 | 数据库设计、Flask-Login 集成等风险可在第 1–2 个迭代验证 |
| 变更成本 | 变更需回溯多个阶段文档 | 变更只影响当前迭代 | 例如"预约状态需增加已评价状态"可在单个迭代内完成 |
| 反馈 | 用户末期才看到系统 | 用户每轮迭代可试用 | 教师可逐实验检查，及时纠偏 |

**结论**：本项目需求粒度粗、技术栈需要边学边用、且课程进度强制分批交付，
采用**增量迭代**能把大系统拆成"可运行的小增量"，每轮都有可演示成果，风险与返工成本最低。

## 2. 增量划分（与五次实验一一对应）

1. **增量 1（实验一）**：项目骨架 + 配置 + 版本库 → 产出可运行的首页。
2. **增量 2（实验二）**：模块分解 + 测试驱动构造核心业务模块（预约规则、密码策略）。
3. **增量 3（实验三）**：领域模型 + 数据库表结构 + 数据访问层 + 持久化。
4. **增量 4（实验四）**：页面、表单、会话、权限与反馈提示 + 集成测试。
5. **增量 5（实验五）**：重构、系统集成、文档与交付。

每个增量结束时都执行"跑通全部测试 → 提交 Git → 更新文档"三个动作，
保证任何时刻的代码库都是可运行、可追溯的。

## 3. Scrum 角色与活动在本项目中的落地

| Scrum 要素 | 本项目的对应做法 |
| --- | --- |
| 产品负责人（Product Owner） | 课程教师/需求方：确定模块范围与优先级（MoSCoW） |
| Scrum Master | 组长：组织每日简短同步，消除阻塞（如环境安装问题） |
| 开发团队 | 本课程学生（单人开发时，本人兼任三个角色，但仪式不省略） |
| 产品待办列表（Product Backlog） | `docs/02-用户故事列表.md` 中的 US-01 ~ US-22 |
| 迭代计划会（Sprint Planning） | 每个实验开始时挑选本轮用户故事并拆解任务 |
| 每日站会（Daily Scrum） | 记录"昨日完成 / 今日计划 / 阻塞"三问，写在实验日志中 |
| 迭代评审（Sprint Review） | 每个实验结束时演示可运行增量，对照验收标准自检 |
| 迭代回顾（Sprint Retrospective） | 实验小结中的"问题与解决、改进建议"，并落实为下一次重构项 |

## 4. 完成定义（Definition of Done）

一个用户故事只有同时满足以下条件才算"完成"：

1. 代码实现并通过对应单元的自动化测试；
2. 页面/接口可被实际操作验证，错误场景有明确提示；
3. 代码已提交 Git，提交信息说明本次增量内容；
4. 相关文档（结构说明/类图/表结构）已同步更新。
