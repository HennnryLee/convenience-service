# 核心模块（在线预约模块）详细设计与 TDD 记录

> 对应《软件构造》实验二：核心模块详细设计 + 测试驱动开发

## 1. 为什么选在线预约模块

它是系统**业务规则最密集**的模块（日期、时段、容量、重复、状态流转 5 类约束），
也是跨模块协作的中心（依赖用户登录态与服务信息），最适合验证模块化与 TDD 的效果。

## 2. 模块内部函数划分

| 函数 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| `is_valid_slot(slot)` | 时段合法性判定 | 时段字符串 | bool |
| `remaining_capacity(capacity, used)` | 剩余名额计算 | 容量、已占用 | 剩余数（≥0） |
| `can_transition(cur, new)` | 状态流转合法性 | 当前态、目标态 | bool |
| `next_statuses(status)` | 取可达状态集合 | 当前态 | 状态列表 |
| `can_cancel(status)` | 用户可否取消 | 当前态 | bool |
| `validate_new_appointment(ctx, date, slot, today, max_days)` | 汇总校验，统一返回错误清单 | 上下文+输入 | 错误信息列表 |

## 3. 数据结构选择

| 数据 | 选型 | 理由 |
| --- | --- | --- |
| 时段集合 | `tuple`（不可变） | 只读常量，防止运行期被意外修改 |
| 状态机 | `dict[str, set]` 表驱动 | 查表 O(1)，替代 if/elif 链；新增状态只改表 |
| 外部事实 | `@dataclass(frozen=True)` 的 `AppointmentContext` | 一次性封装 4 个查询结果，减少接口参数宽度；不可变对象避免副作用 |
| 校验结果 | `list[str]` 错误清单 | 一次返回全部问题，前端可逐条提示（优于抛异常中断） |
| 日期 | `datetime.date` | 只关心日期粒度，避免时区/时分秒带来的比较误差 |

## 4. 算法选择

- **容量判定**：`max(capacity - used, 0)`，一次减法，O(1)；用钳位保证不返回负数（防御性编程）。
- **状态流转**：集合查表 `new in TRANSITIONS[cur]`，O(1)；未知状态默认拒绝（安全默认原则）。
- **日期窗口**：`(date - today).days` 与常量 `MAX_DAYS_AHEAD` 比较，避免逐日遍历。
- **校验顺序**：服务状态 → 日期 → 时段 → 重复 → 容量，先便宜后昂贵，减少不必要的数据库查询。

## 6. 黑盒验证（等价类划分 + 边界值分析）补充

除 TDD 用例外，按黑盒方法对模块做等价类复核，结果记录于
`docs/../软件测试/实验报告` 中的《黑盒测试与功能测试》报告（与测试课程共用同一被测系统）。

**预约日期等价类**：
| 等价类 | 取值 | 预期 |
| --- | --- | --- |
| 有效 | 今天 ~ 今天+30 | 通过 |
| 无效（过去） | 今天-1 及更早 | 拒绝 |
| 无效（超窗） | 今天+31 及更远 | 拒绝 |
| 无效（空） | None | 拒绝并提示选择日期 |

**容量等价类**：剩余 ≥1 通过；剩余 =0 拒绝；超卖（used>capacity）按 0 处理，拒绝。

## 7. 本轮遇到的问题与解决

| 问题 | 现象 | 解决 |
| --- | --- | --- |
| 业务规则与数据库耦合，测试必须起数据库 | 早期写法在函数内直接 `Appointment.query.filter(...)` | 抽出 `AppointmentContext` 由调用方注入，规则层变为纯函数 |
| 日期边界依赖系统当前时间，测试不稳定 | 用例在不同日期运行结果不同 | 为 `validate_new_appointment` 增加 `today` 参数，测试注入固定日期 |
| 状态判断散落为 if/elif | 新增状态要改多处 | 改为 `APPOINTMENT_TRANSITIONS` 查表 |
