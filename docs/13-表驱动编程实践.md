# 表驱动编程实践

> 依据：《基于案例的软件构造教程》4.5.2 表驱动编程
> 实现：`app/utils/constants.py`、`app/utils/table_driven.py`
> 测试：`tests/unit/test_table_driven.py`（32 条）

## 1. 教材要点

教材指出："任何使用逻辑语句的情况都可以用存储了信息的读取表的操作。如果条件简单，
逻辑语句直截了当、易用；逻辑链越复杂，表驱动编程就越有吸引力。使用得当，表驱动编程
把复杂的逻辑编织在表中，而不是编织在代码中，使得程序结构更加简洁、逻辑清晰、容易
修改和扩展。"

教材把查询方式归为三种，本系统各用一个真实场景落地：

| 查询方式 | 教材说明 | 本系统实例 |
| --- | --- | --- |
| 直接访问 | 通过下标直接得到结果或动作 | 分类码 → 分类名 / 角标（`CATEGORY_BADGES`、`SERVICE_CATEGORIES`） |
| 阶梯访问 | 表中存放数据区间，顺序扫描隐含比较 | 价格 → 价格档位（`PRICE_LADDER`） |
| 索引访问 | 先由数据算出索引，再由索引查表 | 耗时分钟数 → 耗时档位（`DURATION_INDEX` + `DURATION_STEPS`） |

## 2. 已被表驱动的规则清单

| 规则 | 表 | 位置 | 表驱动前（若用 if/elif） |
| --- | --- | --- | --- |
| 预约状态流转 | `APPOINTMENT_TRANSITIONS` | `constants.py` | 4 个状态 × 4 个目标 = 16 个分支 |
| 状态中文文案 | `APPOINTMENT_STATUS_TEXT` | `constants.py` | 4 个分支 + 默认 |
| 评价星级文案 | `RATING_TEXT` | `constants.py` | 5 个分支 |
| 服务分类 | `SERVICE_CATEGORIES` | `constants.py` | 5 个分支 |
| 排序方式 | `SORT_OPTIONS` | `constants.py` | 5 个分支 + 白名单校验 |
| 价格档位 | `PRICE_LADDER` | `table_driven.py` | 4 层 if/elif |
| 耗时档位 | `DURATION_INDEX`/`DURATION_STEPS` | `table_driven.py` | 3 层 if/elif |

以状态流转为例，表驱动后判断只剩一行：

```python
def can_transition(current, new):
    return new in APPOINTMENT_TRANSITIONS.get(current, set())   # 查表，无分支
```

新增一个状态（如"已改期"）只需在表中加一行，**业务代码零改动**；若写成 if/elif，
则要同步修改 4 个状态的判断链，遗漏一处就会产生不一致。

## 3. 三种访问方式的实现与边界

### 3.1 直接访问

```python
CATEGORY_BADGES = {"government": "政务", "life": "生活", ...}
def category_badge(code):
    return CATEGORY_BADGES.get(code, "其它")   # 未知码回退，不抛异常
```

边界：未知分类码、`None` 都回退为"其它"（防御性编程，外部数据不可信）。

### 3.2 阶梯访问

```python
PRICE_LADDER = ((0, "免费"), (30, "低价"), (80, "中等"), (150, "较高"))
def price_level(price):
    for upper_bound, label in PRICE_LADDER:
        if float(price or 0) <= upper_bound:
            return label
    return "高价"
```

边界：每个档位的**上界值**（30、80、150）与**上界+ε**（30.01、80.01、150.01）都必须测到，
这正是边界值分析与表结构耦合的地方——见 `test_price_level_ladder` 的 9 组数据。

### 3.3 索引访问

```python
DURATION_INDEX = ("快速", "常规", "较慢", "其他")
DURATION_STEPS = (30, 60, 120)
def duration_index(minutes):
    for index, step in enumerate(DURATION_STEPS):
        if int(minutes or 0) <= step:
            return index
    return len(DURATION_STEPS)
```

边界：0/30/31/60/61/120/121/1000 分钟共 8 组，验证下标映射在每个台阶上都正确。

## 4. 表驱动的验证策略

表驱动把"知识"集中到一处，因此测试也只需验证两件事：

1. **表的正确性**：表项本身是否符合业务规则（等价于需求评审）；
2. **查表函数的正确性**：下标计算/回退分支是否正确。

`tests/unit/test_table_driven.py` 的 32 条用例按此组织，其中一条专门做**实现等价性验证**：

```python
def test_price_level_matches_reference_rule():
    """与朴素 if/elif 规则逐点比对，证明表驱动实现与规则定义等价。"""
```

用参考实现（if/elif 版）对 12 个价位逐点比对，既验证了表，也验证了查表逻辑——
这是"重构不改变行为"的直接证据，与实验五的重构记录相互印证。

## 5. 与页面层的配合

服务详情页不再写分支，而是直接展示查表结果：

```jinja
价格档位：{{ price_level }} · 耗时档位：{{ duration_level }} · 分类：{{ category_text(service.category) }}（{{ category_badge }}类）
```

`get_service_detail()` 在服务层一次性算好三个派生字段，模板只负责渲染——表现层不含业务判断，
符合实验四的分层约定。

## 6. 小结

| 维度 | 表驱动前 | 表驱动后 |
| --- | --- | --- |
| 新增一个分类/档位 | 改 1~5 处判断链 | 改 1 行表项 |
| 分支覆盖测试量 | 分支数 × 2 | 表项数 + 边界 |
| 模板中的业务判断 | 有 | 无 |
| 规则一致性 | 靠人工同步，易漏 | 单一事实来源，不会不一致 |
