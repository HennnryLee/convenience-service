# 重构记录与效果说明

> 对应《软件构造》实验五：软件重构与交付

## 1. 重构前的坏味道识别

| 编号 | 位置 | 坏味道 | 具体表现 |
| --- | --- | --- | --- |
| S-01 | `repositories/*.py`（5 个文件） | 重复代码 | 每个 Repository 都重复写 `db.session.add(x); db.session.commit()`、`setattr` 批量赋值、`db.session.get(Model, id)` |
| S-02 | `modules/admin.py::edit_service` | 过长函数 | 一个视图里同时做"取实体 + 建表单 + 8 个字段赋值 + 分支建/改 + 重名校验"，约 40 行 |
| S-03 | `modules/*.py` | 魔法数字 | `per_page=10`、`per_page=9` 散落在 5 个视图中，改分页大小要改多处 |
| S-04 | `repositories/appointment_repository.py::list_all` | 冗长条件 | 4 个连续的 `if xxx: stmt = stmt.where(...)`，新增筛选条件要继续加 if |
| S-05 | `modules/services.py::detail` | 命名不规范 | 局部变量 `detail` 与视图函数名同名，可读性差 |

## 2. 重构手法与实施

### 重构 1：提炼超类 + 方法上移（Extract Superclass / Pull Up Method）—— 针对 S-01

**动机**：5 个 Repository 中重复代码约 40 行，任何一处提交逻辑变更都要改 5 个文件。

**操作**：新建 `app/repositories/base.py` 定义 `BaseRepository`（含 `add / save / delete / get / update / count_all`），
5 个子 Repository 继承它并设置 `model` 属性，删除各自重复的样板代码。

```python
# 重构前（每个 Repository 各写一遍）
@staticmethod
def add(user, commit=True):
    db.session.add(user)
    if commit:
        db.session.commit()
    return user

# 重构后
class UserRepository(BaseRepository):
    model = User          # 通用 CRUD 全部继承
```

**效果验证**：`pytest` 75 条用例全部通过；`app/repositories/` 代码行数由 402 行降至 316 行（−86 行，−21%）。

### 重构 2：提炼函数（Extract Method）—— 针对 S-02

**动机**：`edit_service` 视图函数过长，混合了"字段映射"与"流程控制"两类职责。

**操作**：提炼 `_build_service_payload(form)`，视图只保留流程：

```python
def _build_service_payload(form):
    return dict(name=form.name.data.strip(), category=form.category.data, ...)

# 视图中
if form.validate_on_submit():
    payload = _build_service_payload(form)
```

**效果验证**：函数长度由 40 行降至 22 行，圈复杂度由 6 降至 3；`pytest tests/integration` 全通过。

### 重构 3：以常量替换魔法数字（Replace Magic Number with Symbolic Constant）—— 针对 S-03

**操作**：在 `config.py` 增加 `ITEMS_PER_PAGE / USER_ITEMS_PER_PAGE / ADMIN_ITEMS_PER_PAGE`，
视图中所有 `per_page=10` 改为引用常量。

**效果验证**：分页相关集成测试全部通过；后续调整分页大小只需改一处配置。

### 重构 4：以表驱动替换条件表达式 —— 针对 S-04

**操作**：

```python
@staticmethod
def _apply_filters(stmt, filters):
    field_map = {"user_id": Appointment.user_id, "service_id": Appointment.service_id,
                 "status": Appointment.status, "appointment_date": Appointment.appointment_date}
    for key, value in filters.items():
        if value is not None and key in field_map:
            stmt = stmt.where(field_map[key] == value)
    return stmt
```

**效果验证**：`list_by_user` 与 `list_all` 复用同一过滤器；新增筛选条件只需在 `field_map` 加一行。

### 重构 5：重命名变量（Rename Variable）—— 针对 S-05

`services.detail` 中的 `detail` 改为 `service_detail`，消除与视图函数名的混淆。

## 3. 重构效果汇总

| 指标 | 重构前 | 重构后 | 变化 |
| --- | --- | --- | --- |
| `app/repositories/` 总行数 | 402 | 316 | −86（−21%） |
| 重复代码（`add/commit` 样板） | 5 处 | 1 处（基类） | −4 处 |
| `edit_service` 函数长度 / 圈复杂度 | 40 行 / 6 | 22 行 / 3 | −45% / −50% |
| 分页魔法数字 | 5 处 | 0 处（3 个常量） | 全部消除 |
| 自动化测试 | 75 通过 | 75 通过 | **功能保持不变** |

> 每次重构后均执行 `pytest` 全量回归，全部 75 条用例通过，确认重构未改变外部行为。

## 4. 尚未重构的遗留项（改进建议）

| 项目 | 问题 | 建议 |
| --- | --- | --- |
| 视图层仍承担少量查询 | `main.index`、`services.list` 直接调用 Repository | 后续可引入"应用服务层"统一编排，视图只做渲染 |
| 缺少数据库迁移脚本 | 现用 `db.create_all()` | 引入 Flask-Migrate，便于生产环境平滑升级 |
| 静态样式与逻辑未分离 | CSS 内联类名较多 | 引入组件化样式约定或前端构建工具 |
